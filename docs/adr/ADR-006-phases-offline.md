# ADR-006: Фазы реализации; фаза 1 — офлайн-минимум для ручного прогона на MOCK

- **Статус:** Принято (2026-10-14)
- **Дата:** 2026-10-14
- **Контекст принятия:** решение владельца при планировании батча сессий реализации (2026-10-14); перекраивает дорожную карту PLAN.md §11 (этапы M1–M5 → фазы) и режим разработки
- **Связанные документы:** `PLAN.md` §11 (синхронно правится), §4.3, §10, §13; ADR-005 (SDK), ADR-002 (lint-гейт); сессии M01–M07

---

## 1. Контекст

Разработка стартует **без доступа к SAP-системе**: код нельзя создать в
системе и выгрузить abapGit'ом, как предполагалось раньше. При этом репозиторий
уже готов к обратному направлению — `src/` + `.abapgit.xml` + abaplint-гейт
(ADR-002). Одновременно владельцем принято: первым смысловым куском нужна не
вся дорожная карта (M1–M5), а **минимум для ручного запуска бенчмарка и
просмотра логов**, и вместо реального SDK (установка — BL-1) достаточно MOCK.

## 2. Решение

**А. Три фазы вместо этапов M1–M5** (соответствие: M1+M2 → фаза 1 без smoke
реального SDK; smoke+M3+M4 → фаза 2; M5 → фаза 3):

1. **Фаза 1 — MVP ручного прогона на MOCK**: DDIC, импорт задач,
   LLM-клиент (только `ZCL_AI_LLM_MOCK`), движок фазы 1 (CANON, CHECK,
   цикл, персистентность, resume, ENQUEUE), ручной запуск `ZAI_RUN` и
   просмотр логов `ZAI_STATUS`. Сессии M01–M07; последняя (M07) — деплой в
   систему и сквозная приёмка.
2. **Фаза 2 — реальные модели и регулярность**: BL-1 (установка
   aisdkforsapabap), `ZCL_AI_LLM_SDK_PROXY`, реестр реальных моделей
   (решение владельца), первый реальный прогон, `ZAI_REPORT` (тренды,
   алерты, CSV), планировщик, транзакционные коды (PLAN.md §13.4).
3. **Фаза 3 — юнит-тесты** (фаза 2 бенчмарка): `Z_AI_RUN_TESTS`,
   `ZCL_AI_ASSERT`, галка `EXECUTE_UNIT_TESTS`, метрики UnitOK.

**Б. Офлайн-режим разработки.** ABAP-код пишется прямо в `src/` в формате
abapGit (FOLDER_LOGIC=FULL, контракт `.abapgit.xml`), включая DDIC-объекты
как сериализованные XML (`.tabl.xml`, `.dtel.xml`, `.enqu.xml`). Деплой в
систему (abapGit pull, активация, генерация SM30-видов, прогоны) — человек,
сессия M07. Единственная локальная верификация — abaplint-гейт
(`make lint`); семантики (DDIC-активация, `SYNTAX-CHECK`, авторизации) он не
проверяет — всё системное считается непроверенным до M07 и фиксируется в
отчёте сессии как «проверить в системе». SM30-виды обслуживания генерируются
в системе на M07 (SE54), офлайн не пишутся.

**В. Настройки — дефолты в коде.** Новый объект `ZCL_AI_SETT` (внесён в
PLAN.md §10): чтение `ZTAI_SETT` с fallback на дефолты §4.3, зашитые в коде.
Засев таблицы настроек для первого прогона не нужен; строки `ZTAI_SETT` —
override без кода. Строка реестра `ZTAI_MODEL` для MOCK создаётся на M07
(SM30 после генерации вида).

**Г. Фаза 1 не включает** реальный SDK: `ZCL_AI_LLM_SDK_PROXY`, BL-1 и
smoke с реальным LLM — фаза 2 (ADR-005 без изменений).

Синхронные правки: `PLAN.md` §2, §4.3, §10, §11, §13; `AGENTS.md`
(офлайн-режим); `docs/sessions.md` + файлы сессий M01–M07 (перепланировка
батча).

Последствия: положительные — начало реализации не блокировано доступом к
системе; фаза 1 даёт проверяемый end-to-end контур на MOCK; lint-гейт
становится рабочим (в `src/` появится код). Отрицательные/риски — DDIC-XML
руками: опечатки увидит только активация на M07 (купируется сверкой с
образцами выгрузки zvvvv-abab-vectors и правилом `check_ddic`/`xml_consistency`
в гейте); часть решений (STRING в `SYNTAX-CHECK`) проверяется только на M07.
Критерий пересмотра: появление постоянного доступа к системе (тогда M07
превращается из «деплой всего батча» в короткую приёмку после каждой сессии).

## 3. Сравнение по осям решения

| Ось | Фазы + офлайн (принято) | Как прежде: этапы M1–M5, код в системе |
|---|---|---|
| Старт без доступа к системе | да | нет (блокер) |
| Первый видимый результат | ручной прогон на MOCK (фаза 1) | после M2 |
| Площадь поверхности риска DDIC-XML | ручная сериализация | нулевая (генерит abapGit) |
| Проверка системных гипотез (STRING, CVERS) | отложена в M07 | по ходу |

**Итог сверки:** решающая ось — старт без системы; риск ручного DDIC-XML
ограничен фазой 1 и одним пакетом объектов.

## 4. Рассмотренные варианты

### Вариант A — ждать доступа к системе
Отвергнут: блокирует всю реализацию на неопределённый срок.

### Вариант B — фаза 1 целиком в системе, как прежде
Отвергнут: то же ожидание доступа; противоречит решению владельца.

### Вариант C — офлайн-фаза 1 на MOCK, детальными сессиями ✅ **ПРИНЯТО**
Основание: §2. Батч сессий M01–M07 перепланирован (M01 переписан с
«работы в системе» на офлайн-DDIC).
