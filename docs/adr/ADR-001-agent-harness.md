# ADR-001: Внедрение агентного харнесса (сессии, ADR, беклог, make-гейты)

- **Статус:** Принято (2026-10-14)
- **Дата:** 2026-10-14
- **Контекст принятия:** этап M0 (план, задачи, конвертер) вёлся без машинной дисциплины; перед M1+ (реализация в SAP, недели работы агента) нужен воспроизводимый контур состояния и верификации
- **Связанные документы:** `PLAN.md` (канон), `AGENTS.md` (точка входа), `harness/README.md` (состав и команды)

---

## 1. Контекст

Проект развивается итерациями агента. Состояние после M0 жило в памяти агента и
в двух файлах без статусов: статусы работ не верифицировались, критерии закрытия
оценивались «на глаз», находки вне скоупа терялись. Впереди M1–M5 — длинные
этапы с доступом к SAP-системе, где агент работает вперемежку с владельцем:
без внешней верификации «сделано» неотличимо от «кажется сделанным».

## 2. Решение

**Взять портативный агентный харнесс из `zvvvv-abab-vectors`: рутины
Clock-In/Clock-Out в `AGENTS.md`, статусная модель сессий (⬜/◐/✅, WIP=1),
ADR-реестр, беклог и машинные make-гейты.** Состояние проекта переносится в
`docs/sessions.md` (один источник), закрытие сессии — только через зелёный
`make verify-session`.

Отличия от исходника (осознанные, по решению владельца):

1. **Веточная дисциплина исключена** — агент не создаёт, не переключает и не
   мержит ветки; работа в текущей ветке, push — по явному запросу владельца.
2. **abaplint не подключается** — в репозитории нет ABAP-кода; роль статического
   гейта выполняет новый `check_tasks.py` (формат задач + дословность PROMPT
   по исходному датасету).

Последствия: положительные — состояние верифицируемо, критерии закрытия
машинные, находки не теряются (беклог); отрицательные/риски — накладные
расходы на ведение статусов и шаблонов (компенсируется гейтами, которые ловят
рассинхрон); критерий пересмотра — если дисциплина начнёт тормозить одиночную
работу больше, чем ловит ошибок.

## 3. Сравнение по осям решения

| Ось | Харнесс (сессии + гейты) | Без харнесса (как в M0) | Вывод |
|---|---|---|---|
| Состояние | `docs/sessions.md` — один источник, машинно проверяемый | память агента + разрозненные файлы | критично для M1–M5 |
| Качество закрытия | `make verify-session`, чекбоксы по факту | «на глаз» | гейт внешнний, не субъективный |
| Знание решений | ADR-реестр с трассировкой | разбросаны по переписке | дешевле, чем восстановление |
| Накладные расходы | статусы, шаблоны, гейты (stdlib) | нулевые | приемлемо |

**Итог сверки:** оси состояния и качества критичны (проект на недели/месяцы),
расходы малы; расхождение с исходником ограничено двумя пунктами выше.

## 4. Рассмотренные варианты

### Вариант A — харнесс как в исходнике (с веточной дисциплиной и abaplint)
Отвергнут. Веточная механика избыточна (один исполнитель, решение владельца —
работать без самостоятельного ветвления); abaplint неприменим — ABAP-кода в
репозитории нет.

### Вариант B — облегчённый: только `make check` без сессий/беклога/ADR
Отвергнут. Остаётся главная проблема — состояние в памяти агента; гейты без
модели состояний нечего проверять.

### Вариант C — портативный харнесс, адаптированный (без веток; `check_tasks.py` вместо abaplint) ✅ **ПРИНЯТО**
Основание: см. §2. Механика гейтов и шаблоны перенесены дословно; отличия
минимальны и локальны.
