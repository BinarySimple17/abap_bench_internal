# ADR-005: LLM SDK — Microsoft AI SDK for ABAP; адаптер `ZCL_AI_LLM_SDK_PROXY`

- **Статус:** Принято (2026-10-14)
- **Дата:** 2026-10-14
- **Контекст принятия:** решение владельца до старта M1; отменяет пункт «LLM SDK — собственный» из PLAN.md §1 и уточняет имя адаптера из ADR-004
- **Связанные документы:** `PLAN.md` §1/§2/§11/§13 (синхронно правится этим ADR), ADR-004 (конвенция имён), BL-1 (установка SDK)

---

## 1. Контекст

По прежнему решению SDK предполагался собственный («автор даст исходники»),
адаптер — `ZCL_AI_LLM_SDK`. Исходники не переданы; тем временем доступен
готовый OSS-вариант: **Microsoft AI SDK for SAP ABAP**
([microsoft/aisdkforsapabap](https://github.com/microsoft/aisdkforsapabap) —
MIT, v2.0, активная разработка): вызов LLM из ABAP, провайдеры Azure OpenAI
и OpenAI, распространяется abapGit-репозиторием (`src/` + собственный
`.abapgit.xml`). Владелец решил остановиться на этом SDK как на **общем
случае**.

Объекты SDK — чужой код в Z-неймспейсе: в наш репозиторий он не
синхронизируется и ставится в систему отдельно (abapGit, отдельный пакет).
Поэтому наш адаптер — по сути прокси над внешним SDK, и имя `ZCL_AI_LLM_SDK`
уточнено до `ZCL_AI_LLM_SDK_PROXY`.

## 2. Решение

1. **LLM SDK = Microsoft AI SDK for ABAP** — общий случай; ставится в
   dev-систему отдельно через abapGit (BL-1: выбрать пакет под SDK — не наш
   `ZAI`, проверить пересечения имён с нашими `Z*AI_*`, установить,
   активировать, зафиксировать версию).
2. **Наш адаптер — `ZCL_AI_LLM_SDK_PROXY`** (вместо `ZCL_AI_LLM_SDK`): за
   `ZIF_AI_LLM_CLIENT` инкапсулирует вызовы SDK (клиент/провайдер/конфиг из
   `ZTAI_MODEL-SDK_PROFILE`), отдаёт движку latency/tokens/версию модели
   (PLAN.md §6). SDK-специфика не просачивается в движок.
3. До установки SDK движок отлаживается на `ZCL_AI_LLM_MOCK` — как и прежде.

Синхронные правки: `PLAN.md` §1 (строка «LLM SDK»), §2 (диаграмма), §11 (M1),
§13 (закрыто); `AGENTS.md`; `docs/sessions/M01_session.md`; ADR-004 — отметка
v2 (имя из его таблицы переименования уточнено этим ADR).

Последствия: положительные — готовая реализация протоколов/аутентификации
OpenAI/Azure OpenAI, меньше своего кода; общий случай зафиксирован, движок
не ждёт «исходники от автора». Отрицательные/риски — SDK в активной
разработке (API может меняться: правки локализуются в прокси), провайдеры
пока только OpenAI/Azure OpenAI (выбор стартовых моделей — §13.2), чужой
Z-код в системе (проверка коллизий имён при установке — BL-1). Критерий
пересмотра: смена провайдеров или SDK владельцем.

## 3. Сравнение по осям решения

| Ось | Microsoft AI SDK + прокси (принято) | Собственный SDK (прежде) | Прямые HTTP-вызовы без SDK |
|---|---|---|---|
| Готовность к M2 (smoke с реальным LLM) | высокая (ставится abapGit) | низкая (исходников нет) | средняя (писать с нуля) |
| Объём своего кода | только прокси | весь SDK | клиент, auth, ретраи |
| Зависимость от внешнего репозитория | да (MIT, активная разработка) | нет | нет |

**Итог сверки:** решающие оси — готовность и объём своего кода; изменчивость
чужого API купируется прокси-адаптером.

## 4. Рассмотренные варианты

### Вариант A — собственный SDK (прежнее решение)
Отвергнут: исходники не переданы и сроков нет; держать движок в ожидании —
блокер для M2 (smoke с реальным LLM).

### Вариант B — HTTP-клиент напрямую, без SDK
Отвергнут: повторяет то, что SDK уже даёт (аутентификация, форматы,
ретраи); свой код — свои баги.

### Вариант C — Microsoft AI SDK for ABAP + наш прокси ✅ **ПРИНЯТО**
Основание: §2. Имя адаптера отражает роль — прокси над внешним SDK.
