# AGENTS.md — abap_bench_internal (точка входа агента)

Внутренний LLM-бенчмарк ABAP, исполняемый целиком внутри SAP-системы
(еженедельный мониторинг моделей по генерации ABAP-кода). Работа ведётся
итерациями-сессиями; состояние проекта живёт в `docs/sessions.md`, не в памяти
агента. Инфраструктура агента — [ADR-001](docs/adr/ADR-001-agent-harness.md).

**Первым делом читать `PLAN.md`** — канон: архитектура, формат задач, таблицы,
метрики, дорожная карта, открытые вопросы. Этот файл — рутины агента.

**Приоритет источников при конфликте:** `PLAN.md` → `docs/adr/` (индекс:
`docs/adr/README.md`) → сессии `docs/sessions/` → `backlog/`. Беклог не
переопределяет решения — предлагает будущие. Текущее состояние проекта — блок
«Текущее состояние» в `docs/sessions.md`.

ABAP-код (префиксы `Z*AI_*` — [ADR-004](docs/adr/ADR-004-naming-convention.md),
список имён — PLAN.md §10) создаётся в SAP-системе и
попадает в репозиторий выгрузкой abapGit в `src/` (FOLDER_LOGIC=FULL,
контракт синхронизации — `.abapgit.xml`); перенос в обе стороны делает
человек. Локально системы нет: автоматическая верификация ABAP — abaplint
(`abaplint.json` — гейт, `abaplint-all.json` — репорт); всё, что требует
системы (запуск, DDIC-активация, авторизации, RFC), фиксируется в отчёте
сессии как «проверить в системе» — никогда не считается проверенным.

## Verification

```bash
make check                  # lint-гейт + гейт задач + машинные гейты харнесса
make lint                   # только abaplint-гейт (abaplint.json)
make lint-all               # широкий линт (стилистика/нейминг) — репорт, не блокирует
make check-tasks            # только гейт формата tasks/*.task.txt
make check-sessions         # аудит сессий без полного check
make verify-session S=M01   # гейт закрытия сессии: lint + задачи + чекбоксы/статусы
make session-archive        # перенос ✅-строк сессий в архив
make backlog-archive        # перенос закрытых элементов беклога в архив
make setup                  # npm install (@abaplint/cli) — один раз
```

Репозиторий консистентен, когда `make check` завершается с кодом 0.
Зависимости: python stdlib (гейты) + `@abaplint/cli` (`make setup`). Гейты:
abaplint (ABAP в `src/`; без файлов — пропуск), `check_tasks.py` (формат задач +
дословность PROMPT по исходному датасету), `check_sessions.py` (WIP=1,
статусы, даты), `backlog_archive.py --check`, `session_archive.py --check`
(гигиена архивов).

**Границы верификации:** abaplint — синтаксис, консистентность объектов/XML,
naming, часть семантики; он не выполняет код и не знает DDIC целевой системы:
«зелёный lint» ≠ «работает в системе», и он не ловит все конструкции 7.55+
(см. ADR-002). Python-гейты проверяют только репозиторий (формат задач,
дисциплину, согласованность документов). Всё, что требует SAP (запуск,
DDIC-активация, авторизации, RFC), фиксируется в «Отчёте» сессии как
«проверить в системе» — никогда не считается проверенным.

## Ключевые правила (канон — PLAN.md)

- **Фаза 1 = syntax-only**: код LLM проверяется только `SYNTAX-CHECK FOR itab`,
  исполнение сгенерированного кода (`INSERT REPORT`, `SUBMIT`,
  `GENERATE SUBROUTINE POOL`) в движке фазы 1 запрещено.
- Юнит-тесты (фаза 2) — исключительно за настройкой `EXECUTE_UNIT_TESTS`,
  по умолчанию выключена.
- **Система — NetWeaver 7.54** (та же dev-система, что у zvvvv-abab-vectors;
  [ADR-003](docs/adr/ADR-003-nw-754.md)): весь ABAP-код — уровень до 7.54,
  конструкции 7.55+ запрещены (например, `FINAL(...)`); `NW_VERSION` в system
  prompt = 7.54 — модель обязана генерировать под эту версию. Локальный гейт —
  abaplint v754 ([ADR-002](docs/adr/ADR-002-abaplint-gate.md)).
- LLM SDK — Microsoft AI SDK for ABAP ([aisdkforsapabap](https://github.com/microsoft/aisdkforsapabap)):
  ставится в систему отдельно (abapGit, ADR-005, BL-1); наш адаптер — прокси
  `ZCL_AI_LLM_SDK_PROXY` за `ZIF_AI_LLM_CLIENT`; до установки SDK движок
  отлаживается на `ZCL_AI_LLM_MOCK`.
- Задачи добавляются через файлы `tasks/*.task.txt` + импорт (формат в
  PLAN.md §4.1). Содержание задач после включения в бенчмарк не меняется —
  только `task_version` через реимпорт; тренды считаются в пределах
  одинакового `TASKSET_HASH`.
- Промпты задач — дословные Python-спекки из исходного бенчмарка; язык
  взаимодействия с LLM в заданиях/prompts — английский, рабочая
  документация — русская.
- Аналогии с Python-бенчмарком: состояния диалога S/X/I ≈ Success/MaxedOut/
  Infra из `chat_state.py`; каноникализация ≈ `abap_interaction.py`
  (extract_contract / canonicalize_code / remove_code_blocks).

## Clock-In (начало сессии)

1. `pwd` — подтверди корень репозитория.
2. `PLAN.md` — §11 (дорожная карта) и §13 (открытые вопросы); `docs/sessions.md`
   — блок «Текущее состояние» + таблица; найди свою сессию.
3. Прочитай файл своей сессии целиком: ⚠️ Прочитай → Правила → Предусловия →
   Задачи → Ловушки.
4. `git log --oneline -5` — что произошло после последней сессии.
5. `make check` — baseline должен быть зелёным; красный → сначала чини,
   не добавляй нового.
6. Ровно одна сессия в работе на трек (WIP=1) — `make check` это проверяет.
7. Git: работай в текущей ветке; **ветки не создавай и не переключай**
   (см. «Git-дисциплина»).

## Clock-Out (конец сессии)

1. Отметь чекбоксы сессии по факту (Предусловия/Задачи/Критерии приёмки).
2. Обнови статусы: шапка файла сессии (`Статус:`), строка в таблице
   `docs/sessions.md` (◐ в работе / ✅ + дата ГГГГ-ММ-ДД), блок
   «Текущее состояние».
3. `make verify-session S=<ID>` — незакрытых чекбоксов нет, статусы согласованы.
4. Сессия закрыта ✅ → `make session-archive` (перенос строки в
   `docs/sessions-archive.md`).
5. `make check` — зелёный.
6. Коммит в текущую ветку с сообщением, объясняющим **WHY** (не только что
   изменено); репозиторий оставь перезапускаемым через `make check`.
7. Всё обнаруженное вне скоупа сессии — в `backlog/`, не «сделаю по пути».
8. Всё, что требует реальной системы, — списком в «Отчёт» сессии, пункт
   «Проверить в системе».

## Фиче-дисциплина (сессии = фичи)

- Состояния: ⬜ не начата → ◐ в работе → ✅ завершена (+дата ГГГГ-ММ-ДД);
  пропускать состояния нельзя.
- **WIP=1**: не более одной ◐ на трек (первая буква ID) — машинно проверяет
  `make check`.
- **Гейт качества**: ✅ ставится только после зелёного
  `make verify-session S=<ID>` — никогда «напрямую», минуя ✅ Самопроверки и
  Критерии приёмки сессии.
- Одна сессия = одна итерация агента. Не влезает — режь сессию и переноси
  остаток в отчёт, а не распыляйся на соседние.

## Git-дисциплина (без веточной модели)

- **Агент не создаёт, не переключает и не мержит ветки** — работа ведётся в
  текущей ветке репозитория. Если владельцу нужна ветка, он называет её сам;
  тогда заполняется поле «Ветка» в шапке сессии.
- Коммиты — на задачу или логическую группу, сообщения объясняют **WHY**;
  push — только по явному запросу владельца.
- Запрещены без явного запроса владельца: `git push --force`, `git reset --hard`,
  rebase/cherry-pick, `rm -rf`.

## Definition of Done

Задача/сессия закрыта, когда: ✅ Самопроверки задач выполнены по факту;
Критерии приёмки сессии выполнены; `make check` и `make verify-session S=<ID>`
зелёные; затронутые документы обновлены (`PLAN.md`/ADR/sessions — доки идут
вровень с работой); статусы обновлены (шапка + таблица + «Текущее состояние»);
коммит объясняет WHY; шаги, требующие системы, явно перечислены в отчёте.
**«Код/правки написаны» ≠ «готово»** — только внешняя верификация, не
уверенность агента.

## Жёсткие ограничения

- Без явного запроса владельца запрещено: `rm -rf`, `git push --force`,
  `git reset --hard`, изменения вне зоны своей сессии/трека.
- Файлы `.abapgit.xml`, имена и пакетная принадлежность объектов — не менять
  без ADR: это контракт синхронизации с системой.
- Ослабление lint-гейта (исключения/правила abaplint) — только через ADR.
- Изменение харнесса (`harness/`, корневой `Makefile`, машинные гейты, формат
  сессий/беклога) — ADR в той же работе, не «попутно».
- Изменение канона (`PLAN.md`, в т.ч. зафиксированных решений §1) — через ADR
  с синхронной правкой `PLAN.md`; канон приоритетнее сессий.
- Содержание задач `tasks/*.task.txt` после включения в бенчмарк не меняется;
  правки файлов задач — осознанно (конвертер или ручная правка) и только под
  зелёным `make check-tasks` (проверит контракт `lcl_solution` и дословность
  PROMPT).
- Новая внешняя зависимость python-кода (`tools/`, `harness/scripts/`) —
  сначала ADR (обоснование, версия, альтернативы); по умолчанию — stdlib.

## Правила кодирования

**ABAP (в SAP-системе)** — перед написанием/правкой сверяйся с
`docs/ABAP-PITFALLS.md` — грабли языка, DDIC и A4H/ADT, проверенные на этом
стенде 7.54: SORT без BY на EMPTY KEY, целочисленное деление, `sy-*` в
параметры без VALUE, APPEND в SORTED-таблицу, пределы abaplint и др. Найденные
новые грабли дополняют тот файл в тот же день (нумерация — сквозная, N65+).
Справочная память — полный читшит SAP, локальная копия в
`docs/reference/abap-cheat-sheets/` (в `.gitignore`; нет папки — `git clone
--depth 1 https://github.com/SAP-samples/abap-cheat-sheets` туда же), таблица
«тема → файл» — `docs/reference/README.md`; семантику SQL и языка сверять
обязательно — abaplint её не проверяет (PITFALLS #13, #64). Скилл
`/abap-memory` — маршрут по этим справочникам. Уровень до 7.54 (PLAN.md §3,
ADR-003): конструкции 7.55+ запрещены (например, `FINAL(...)`); гейт —
abaplint (`make lint`, `syntax.version v754`), но он не отсекает все новейшие
конструкции и не компилятор (PITFALLS #13) — не полагайся только на него;
имена объектов — только из PLAN.md §10; магические значения — в именованные
константы; `sy-subrc` проверять сразу после операции; исключения —
`RAISE EXCEPTION TYPE zcx_...`, не смешивать `MESSAGE E` с ОО-обработкой
ошибок.

**Python** (`tools/`, `harness/scripts/`): только stdlib; пути резолвятся от
скрипта (`REPO = parents[2]`), запуск — из любого каталога; консоль Windows —
форсирующий `reconfigure(encoding="utf-8")`; любое нарушение — exit 1,
сообщение объясняет, что исправить.

## Warnings

- **Контекст тает** — не торопись «закрыть» сессию к концу окна: лучше
  остановись, обнови «Текущее состояние» и файл сессии, закоммить чистый
  checkpoint.
- Закрытие на глазок хуже честного ◐ — статус отражает факт, а не намерение.
- Не ослабляй гейты ради зелёного статуса (исключения — только через ADR) —
  это регресс харнесса.
- Не доверяй «гейты зелёные» = «работает в системе»: гейты не знают SAP;
  спорные места — в «Проверить в системе» отчёта сессии.
