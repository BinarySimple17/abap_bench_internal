# ADR — Architecture Decision Records

Индекс архитектурных решений проекта. Приоритет источников при конфликте:
канон продукта → этот каталог → сессии `docs/sessions/` → `backlog/`.

## Как читать ADR (двухслойная модель)

- **Тело** — для человека: контекст → альтернативы → решение → последствия,
  связный текст без внутренней кухни.
- **Блок «Трассировка»** в конце — для машин (агентов) и точной навигации:
  ID-ссылки на сессии/беклог/ревизии в одну-две строки. Человек его пропускает;
  агент парсит.
- Подробная история правок — в git и `docs/sessions-archive.md`, в теле ADR
  не дублируется. Новые ADR пишутся сразу по этой модели; при правке старых —
  тело переводится на неё.

## Как заводить новый ADR

1. Номер — следующий по порядку; файл — `ADR-0NN-краткое-имя.md` в этой папке
   (шаблон — `_template.md`).
2. Формат — как в шаблоне: заголовок, **Статус** (с датой и версией), дата,
   контекст принятия, связанные документы, контекст, решение, сравнение по осям,
   рассмотренные варианты, трассировка.
3. Тело — для человека: абзацы ≤120 слов, без внутренних ID сессий/беклога в
   прозе; ID-ссылки — в блок «Трассировка» в конце (см. принятые ADR).
4. Изменение уже принятого ADR — новая версия в том же файле с датой (история
   версий — в «Статусе»), не тихая правка.
5. Если решение меняет пункт канона продукта — синхронная правка канона в той
   же работе (канон приоритетнее ADR).
6. Добавь строку в реестр выше.
